# Vue3-Admin 项目模拟面试与亮点解析

在面试中介绍该项目时，不要只按部就班地说“我用了Vue3和Element Plus”。而应该采用 **STAR法则**（情境、任务、行动、结果），主动引导面试官关注你的**架构设计、工程化基建和解决复杂问题的思路**。

由于中后台项目往往不以“花哨的动画”取胜，而是以**“严谨的权限”、“稳定的请求”、“极佳的开发体验”**为核心亮点。以下是为您准备的模拟面试 QA。

---

## 💡 亮点一：企业级权限控制与双模路由设计

**👨‍💼 面试官：看你的项目里写了中后台管理系统，你们的路由和菜单权限是怎么设计的？**

**🙋‍♂️ 高分回答：**
“在我们的系统中，因为产品形态面对不同的客户（有些是轻量级后端，有些是拥有严格 RBAC 模型的政企中台），所以我设计了**『前端静态管控』与『后端动态注入』的双模路由机制**。
1. **解耦设计**：我将像登录、404 等页面抽离为白名单基础路由。而业务模块路由，我没有写死在特定的文件里，而是使用 Webpack 的 `require.context` 自动化扫描 `views/modules` 下的路由配置进行归集。
2. **后端主导模式（核心逻辑）**：登录拿到 Token 后，在 `router.beforeEach` 守卫中拉取后端返回的用户菜单权限树。然后，我在前端写了一个比对算法（`transformMenuTreeToRoutes`），将后端返回的精简路径节点与前端扫描到的完整路由池进行深度遍历比对。
3. **动态渲染**：比对成功后，附加上后端的排序字段 `sort` 进行路由重排。最终借用 Vue Router 4 的 `router.addRoute` API，动态挂载到 `Layout` 架构下，同时把这棵树存入 Pinia 以供侧边栏菜单和 TagsView 标签页渲染。”

**🎯 面试官追问：如果在跳转中途用户刷新了页面，Pinia 里的动态路由丢失了怎么办？**
**🙋‍♂️ 应对策略：**
“我在全局的路由守卫 `beforeEach` 中做了拦截判断，如果监测到有 Token 但是 Store 里的 `routesTree` 长度为 0，就会判定此时是刷新导致的丢失。系统会挂起当前的路由跳转，重新触发一次异步的生成菜单树与 `addRoute` 方法，然后再执行 `next({ ...to })` 将用户带回本来想去的页面，对用户来说是无感知的。”

## 💡 亮点二：现代全自动导入与极致构建体验

**👨‍💼 面试官：你们项目中用到了 Element Plus，如果使用全局注册会导致包体积过大，如果是按需引入，每次都要 import 又很繁琐。你是怎么平衡构建体积和开发体验的？**

**🙋‍♂️ 高分回答：**
“是的，为了达到真正的『按需打包』和『零负担开发』，我深度定制了 Webpack 的配置：
1. 我们摒弃了传统的全局引入方法，引入了 `unplugin-vue-components` 和 `unplugin-auto-import` 插件。
2. 这使得团队在写 Vue 模板时，可以直接写 `<el-button>`，无需在 `script` 中写任何 import 语句。Webpack 会在编译期自动解析 AST，动态注入组件和对应的 CSS 文件。
3. **解决 TS 报错机制**：因为自动导入会导致 TypeScript 和 ESLint 报『变量未定义』的红线。我配置了插件自动生成 `auto-imports.d.ts` 和 `.eslintrc-auto-import.json`，并将它们集成到系统的 `tsconfig.json` 和 `.eslint` 配置中，完美兼顾了严谨的语法检查和优雅的开发体验。
4. 关于图标，我也采用了相同的策略，使用 `unplugin-icons` 将框架图标全量按需化；对于业务级的自定义 SVG，我配置了 `svg-sprite-loader` 将其打包成雪碧图，大幅减少了 HTTP 请求并发数。”

## 💡 亮点三：严谨的请求层封装

**👨‍💼 面试官：你们系统中的 Axios 是如何进行统一封装的？有没有做防止重复提交的处理？**

**🙋‍♂️ 高分回答：**
“中后台存在大量表单，所以请求层的健壮性非常重要。
1. **工厂化封装**：我没有让业务层直接触碰 Axios 实例，而是将暴露出的 `get` / `post` / `put` 等方法做了彻底的二次封装。
2. **状态码拦截**：在响应拦截器 (`response`) 中，拦截并根据规范统一转换 401(Token失效重定向), 403(无权限), 500 等异常，统一抛出系统的 Toast，降低了业务页面的 try-catch 冗余。
3. **防止重复提交（亮点）**：我在二次封装方法外层包了一个自定义的 `windowIt` 高阶函数，配合常量中定义的 `WINDOW_IT_TIME`。通过闭包缓存机制，不仅可以在接口层面实现防抖，还能拦截高频无效请求，从源头上阻止了比如“手抖连续点击两次保存按钮”造成的数据污染。”

## 💡 亮点四：前端工程化与标准化提交

**👨‍💼 面试官：如果让你带一个团队，大家的代码风格参差不齐，你怎么在工程级别保证 Vue 项目的代码质量和 Git 提交的清晰？**

**🙋‍♂️ 高分回答：**
“在这个项目中，我亲自搭建了全套的前端工程化基建护城河：
1. **规范三剑客**：集成了 ESLint 处理 JS/TS 逻辑错误，Prettier 负责统一且死板的换行/引号格式，再加上 Stylelint 处理 CSS/SCSS 的乱写及其 CSS 属性的排列顺序（比如定位属性必须在宽高属性之前）。
2. **拦截关卡 (Husky + lint-staged)**：任何人执行 `git commit` 时，都会触发 `pre-commit` 钩子，不仅只对当前放到暂存区（Staged）的文件进行 Lint 扫描并尝试 auto-fix。如果存在无法修复的报错，提交会被直接回退。
3. **规范提交信息**：我引入了 Commitizen 和 `cz-customizable`。开发者只要敲击 `npm run commit`，终端就会弹出交互式下拉菜单，强制要求选择修改类型 (feat/fix/docs)、影响模块和关联单号。
4. 这套基建带来了极大的收益，我甚至借此搭配 `release-it` 工具，实现了一键自动读取 commit 记录去生成每个版本的 `CHANGELOG.md` 变更日志。”

## 💡 亮点五（真实踩坑加分项）：NPM 包环境与对等依赖冲突的解决

**👨‍💼 面试官提问一个深度的工程能力题：在使用 npm V7 之后，经常在项目里因为 `peerDependencies` 出现 `ERESOLVE unable to resolve dependency tree` 的红字报错，如果是在测试环境和CI上遇到，你一般如何解决？直接加上 `--legacy-peer-deps` 吗？**

**🙋‍♂️ 高分实战回答（建议结合今天我带您处理冲突的经历）：**
“很多同学会无脑加 `--legacy-peer-deps` 来逃避这个问题，但我认为这为线上打包埋下了隐藏炸弹。我习惯从依赖树的根源去解决冲突：
我之前在这个项目中整合全家桶时就遇到过两个典型案例：
1. **依赖包架构异动的废弃插件冲突**：比如原本用于解决格式冲突的插件 `stylelint-config-prettier`，在 Stylelint 升级到 15+ 之后，官方在核心包里直接删除了排版校验，导致该插件完全失效并引发与原本主包的 V14 版本的冲突。我通过查阅 Changelog 确认其废弃后，果断从 package.json 中 uninstall 并修改配置数组将其移出，从根源解决了冲突。
2. **兼容性强制覆盖冲突**：在配置 `ts-jest` 单元测试时，`ts-jest@27` 在自身的 `peerDependencies` 中严格将 `typescript` 锁定在了 `< 5.0` 的版本，但由于我的项目底层基建使用的是 TS 5.0.4，导致出现不能解析的 ERESOLVE 报错。鉴于我在实测中得知 `ts-jest@27` 完全能兼容 TS 5 的部分语法，没有必要强行降级整个项目的 TS，因此我在 `package.json` 中使用了现代 npm 的 `"overrides"` 字段：
```json
"overrides": {
  "ts-jest": {
    "typescript": "$typescript"
  }
}
```
强行将 ts-jest 的内部依赖指向了项目根目录自带的 TS 版本，既优雅绕过了校验，又保证了全局依赖版本的一致性，这是我处理构建抛错的一贯思路体系。”
